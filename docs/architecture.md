# 远程 Skill 基座架构与协议

## 目标与边界

用户在本地 Agent 中以自然语言提出任务。Agent 应能自动发现适用能力、读取必要的项目文件、获得结果、继续本地工作；私有 `SKILL.md`、脚本与服务端模型凭据留在提供方服务器。用户可明确指定连接 Skill，也可由 Agent 根据公开的用途说明自动选择。

“与本地 Skill 一样”主要指**触发方式和任务流程**。远端执行器无法天然读取客户本地磁盘、调用客户已有的本地工具，且多一次网络往返。POC 通过本地桥接器缩小差距：Agent 给任务和路径，桥接器自动发送快照并应用结果。对于需要随时搜索整个项目、运行本地测试或反复询问用户的 Skill，这个 POC 还不等价。

## 组件

| 组件 | 安装位置 | 职责 | 客户可见内容 |
|---|---|---|---|
| 公开连接 Skill | 客户机器 | 意图匹配和调用步骤 | 用途描述、MCP 工具用法 |
| 本地 MCP 桥接器 | 客户机器 | 读取指定文件、远端通信、哈希冲突检查、落盘 | 通用代码与连接配置 |
| 远端 MCP 服务 | 提供方服务器 | 提供工具定义，验证输入，启动执行 | 工具名称、描述、输入输出 Schema |
| 私有 Skill | 提供方服务器 | 真实方法论、脚本、参考材料 | 不作为文件分发 |
| 执行引擎 | 提供方服务器 | Codex、Claude Code、Hermes 或自定义 Agent CLI | 引擎名称可见 |
| 可视化管理台 | 提供方服务器本机 | 编辑服务配置、管理服务进程、查看日志、导出公开连接包 | 客户不可访问 |

每个服务配置为 `{name, description, skill, engine, host, port, timeout_seconds}`，单独监听一个端口。服务端不会把 Skill 文件通过 MCP resource 或 tool 返回。

管理台通过 `nunchaku dashboard` 启动，只绑定 `127.0.0.1`。浏览器调用本机 JSON API；后端复用与 CLI 相同的服务配置校验，原子更新 `services.json`，每个 MCP 服务运行在独立子进程。进程的标准输出和错误输出写到配置文件旁的 `.nunchaku/logs/`。管理台终止时会停止它启动的子进程。客户连接包按服务说明及客户可访问 URL 实时生成；打包内容只有公开连接 Skill、Codex 展示元数据和 `connector.json`。

## 两层协议

### Agent 到本地桥接器

标准 MCP stdio，暴露 `run_skill`：

```json
{
  "task": "把 README 开头写得更清楚",
  "paths": ["README.md"],
  "apply_changes": true
}
```

Agent 不必把文件全文放入模型生成的工具参数。桥接器按配置的项目根目录解析相对路径，只读列出的文件（文本按 UTF-8、其余按 base64 编码发送），拒绝绝对路径、`..`、保留目录和符号链接。调用完成后，桥接器再次检查返回路径和每个原文件的 SHA-256；有冲突时不自动落盘，并将提议交给 Agent 处理。

### 桥接器到远端服务

标准 MCP Streamable HTTP，端点 `/mcp`，执行标准 `initialize → tools/list → tools/call`。`run_skill` 的入参如下：

```json
{
  "task": "把 README 开头写得更清楚",
  "files": [
    {"path": "README.md", "content": "# 原文\n..."},
    {"path": "data.xlsx", "content": "<base64>", "encoding": "base64"}
  ]
}
```

结构化输出：

```json
{
  "service": "my-skill",
  "engine": "codex",
  "answer": "已修改开头。",
  "changed_files": [
    {"path": "README.md", "content": "# 新文\n...", "encoding": "utf-8", "base_sha256": "<输入文件的 SHA-256>"}
  ],
  "deleted_files": [],
  "note": "Changes are proposals. The local Agent must review and apply them in the user's workspace."
}
```

`encoding` 为 `utf-8`（默认）或 `base64`；能按 UTF-8 解码的输出以文本返回，其余用 base64。哈希一律按原始字节计算。新文件的 `base_sha256` 为 `null`。删除文件带路径和原文件哈希。远端只提交**改动提议**，不拥有客户本地文件系统权限。桥接器在成功落盘后只向 Agent 返回简短的已改文件列表；若用户要求预览，可传 `apply_changes: false`，此时结果包含提议内容，其中二进制提议写到 `.nunchaku/proposed/` 下，不内联返回。

协议层不自造 HTTP 端点或 JSON-RPC 方法。将来增加鉴权可沿用 MCP HTTP 的标准授权能力；增加长任务时可扩展为任务 ID 与进度通知，不破坏现有工具的语义。

Codex 对 MCP 工具有独立的审批模式和调用超时。默认超时可能短于服务端的 180 秒执行上限，部署时应调到略高于服务端超时。若要免去每次写入型工具的确认，需要由客户显式将该工具的审批模式设为 `approve`；这代表客户信任桥接器在指定项目根目录内读写文件。

## 为什么组合公开 Skill 和 MCP 桥接器

只装 MCP 时，Agent 可以发现工具，但公开 Skill 提供明确的使用时机、收集哪些路径、如何处理冲突和如何对用户说明。只装一个本地 Skill 时，通常需要把远端请求脚本塞进 Skill，难以获得统一的工具 Schema 和跨 Agent harness 的工具发现。两者组合后，用户仍然用自然语言触发，执行细节不暴露在交互里。

桥接器固定项目根目录，避免让远端服务任意请求本地文件。这个 POC 由本地 Agent 选择必要路径。若一个 Skill 必须在执行中动态读文件、运行本地命令或调用其他本地工具，应升级成双向会话：本地桥接器与远端执行器保持连接，远端发起 `read_file`、`write_file`、`run_command` 等受限请求，本地校验路径和动作后执行。那是下一阶段的协议，不应假定所有 MCP 客户端都支持服务端在单次工具调用内任意回调本地工具。

## 执行流程与错误语义

1. 服务配置验证 Skill 路径、执行引擎、端口及超时。CLI 不接受由客户指定的 Skill 路径或任意命令。
2. 每次调用新建临时目录，只写客户提交的文件快照（按原始字节）和服务端 Skill 副本。
3. 通过所选 CLI 执行任务。CLI 退出非零、超时或不存在时，MCP 返回工具错误；不会返回不完整文件提议。
4. 执行完成后比较输入输出文件；超出 POC 限额或产生符号链接时，返回错误。
5. 本地桥接器只有在所有返回路径的原始哈希都匹配时才自动应用。任何冲突都会阻止本次自动应用。

POC 的落盘操作尚不具备跨多个文件的事务性；在极少数写盘失败或并发修改情况下，可能部分落盘。正式版本应使用临时文件、原子替换及回滚日志，并在请求与结果中加入调用 ID 以支持幂等重试。

## 私有资产保护的真实边界

客户拿不到 `SKILL.md` 文件，但“模型读取私有提示词，再对客户的任意请求作答”并不能保证提示词内容绝不被推断或复述。对高度敏感的算法、数据、权重或模板，应把关键部分放入服务端受控代码或专用工具，只让模型调用有限能力。正式版本还需鉴权、客户隔离、限流、执行容器、出站网络控制与输出审计。当前无鉴权服务默认只监听回环地址，不能直接对公网开放。

## POC 验收

- 同一配置中可定义多个服务，每个服务有自己的 Skill、引擎和端口。
- Codex/Claude Code 能发现 `run_skill`；公开连接 Skill 可作为用户的自然语言入口。
- 客户本地文件内容只在明确列出的路径内传输；私有 Skill 文件不通过响应发送。
- 服务端返回文本文件改动；桥接器正常落盘并在冲突时停止自动应用。
- HTTP MCP 初始化、工具发现、工具调用和 stdio 桥接全链路可自动验证。
- 管理台可在空配置上创建服务，通过页面启动和停止实际 MCP 进程，并导出不含私有 Skill 的连接包。
